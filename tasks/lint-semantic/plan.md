# Plan: lint-semantic

> Spec：[spec/lint-semantic.md](../../spec/lint-semantic.md)（已批准）

## 执行方式

沿用前几个模块：样例知识库由主会话构造，脚本实现派给 Codex，lint SKILL 由主会话修改，真实运行作为 gate。模型判断这一段无法单元测试，所以 gate 里分两步：先在样例上跑，再在真实知识库上跑。

## 任务

### T0 样例知识库（主会话）
- 在 `tests/fixtures/vaults/semantic/` 下构造一个能通过 `kb check`（0 问题）的小知识库，大约 10 页，埋入四类问题，每类配一个**干扰项**：
  - 矛盾：两页现行结论冲突（埋点）；另一对说法看似冲突、其实适用版本不同（干扰）；还有一对已经标了 `[!disputed]`（干扰）；
  - 过期：含版本号、updated 很早的现行句子（埋点）；同样的版本句只出现在 `[!outdated]` 块里（干扰）；
  - 缺页：一个术语在 3 页里出现、但没有页面（埋点）；另一个术语同样多次出现、但已经有自己的 tech 页（干扰）；
  - 升级：被多页链接、log 里更新过 2 次、含"永远不要"祈使句的 pitfall（埋点）；只有祈使句、没有其他信号的页（干扰，由模型判断要不要报）。
- 写一份 README：列出每个埋点和干扰项，以及 pack 和模型各自应该给出的期望结果。
- 内容全部虚构；日期用固定的过去日期，测试里通过参数传入"今天"，避免随时间变化。
- 检查点：report

### T1 实现（派 Codex，--write，期限 1800 秒，后台）
- 内容：`semantic.py`（pack 与 verify）、`kb.py lint semantic-pack | semantic-verify`、`tests/test_semantic.py`、README 补充说明。
- 约束：
  - verify 复用 evidence 模块的逐字比对和 markdown 模块的标注块区域判断，不另写一套；
  - 只读知识库；不碰 `skills/`；原有测试不改且全绿；
  - 测试用临时目录，并设置 `KB_CONFIG`、`KB_STATE_DIR`、`KB_DELEGATE_DIR`，不读本机真实路径（上个模块踩过）；
  - 不联网；不提交。
- 检查点：report

### T2 lint SKILL 和 lint Spec 的变更记录（主会话，与 T1 并行）
- lint SKILL 增加可选的语义段：
  - 什么时候跑；
  - 先 pack，再判断，再 verify；
  - 四类问题的判断标准，以及"不算问题"的情形；
  - 只读核实白名单；
  - findings JSON 格式；
  - Codex 只读沙箱下用 stdin 交给 verify；
  - 只出报告，不改知识库。
- `spec/lint.md` 加一行变更记录。
- 检查点：report

### T3 主会话复核与对抗抽查
- 逐条核验 AC1–AC4、AC7。对抗抽查：
  1. 对样例知识库跑 pack，四类埋点全部出现，干扰项里的标注块内容和已有页面的概念都不出现；
  2. pack 前后知识库文件哈希和 `git status` 不变；
  3. 手写一份 findings：一条真引文、一条改了一个字、一条引自 `[!outdated]` 块、一条页面路径是 `../`。verify 只保留第一条，其余三条单列为剔除；
  4. 往样例里复制大量页面，使 pack 超过 60KB，确认截断生效并在包里注明；矛盾候选不超过 30 对；
  5. 运行时拼接一个假密钥放进 findings 的 reason，报告输出里是打码后的；
  6. 用 `git diff` 确认原有测试没有改动；并在**不设置** `KB_DELEGATE_DIR` 的真实环境下跑全量测试。
- 通读 `semantic.py`；通过后提交，刷新 Codex 缓存。
- 检查点：report

### T4 真实运行（gate，模块最终验收）
- 停下来问你后执行：
  1. AC5：在本会话里，对样例知识库走一遍 `/kb:lint` 的语义段，对照 T0 README 的期望，报告每个埋点有没有命中、干扰项有没有被误报；再故意塞一条编造的引文，确认 verify 把它剔除；
  2. AC6：对你的真实知识库跑一次语义段，报告给你看，由你判断每条是否有用；
  3. 运行前后真实知识库 `git status` 干净、HEAD 不变。
- 检查点：gate

## 风险

| 风险 | 应对 |
|---|---|
| 样例按我自己的理解构造，和真实知识库的写法不一样（delegate-lessons 的 fixture 就漏过真实格式） | T0 的页面按真实知识库里 6 页的写法构造；T4 第 2 步在真实知识库上跑，发现漏判就当场补测试 |
| 模型判断不稳定，同一个包两次跑出的结果不同 | 引文由 verify 兜底，保证不会编造证据；判断标准写进 SKILL；AC5 只要求"埋点至少命中、干扰项不误报" |
| 真实知识库只有 6 页，信号太少，报告可能是空的 | 空报告本身也是有效结论（说明没有问题）；AC6 只要求报告真实，不要求一定有发现 |
| 矛盾候选靠标签和术语交集，可能漏掉用词不同的冲突 | 候选只是线索，模型可以在包里看到全部现行结论，自己补；先上线，等真实数据出来再调 |
