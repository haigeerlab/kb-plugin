# PRD：AI 知识复利系统（PCKS）

> 状态：已批准（2026-11-19） · 日期：2026-11-19 · 阶段：Phase 1（需求再梳理）
> 依据：[Phase 0 调研报告](research/2026-11-19-phase0-research.md)（含第 7 节实跑对比）

## 1. 目标

把干活时产生的经验（bug 根因、技术决策、执行教训）和学到的东西，编译成一个持续生长、互相链接、带出处的个人知识库。新问题、新需求来的时候，人和 AI 都从已有积累起步。高频、已确认的知识升级成规则，让 AI 自动遵守。

**一句话边界**：它解决"积累和调用"，不解决"理解和判断"。

### 1.1 能解决 / 不能解决

| 能解决 | 不能解决 |
|---|---|
| 问题解决完知识就丢了 | 代替你理解和内化 |
| 知识碎片化 | 保证知识正确（关键结论必须验证） |
| 整理太累坚持不下来（记账交给 AI） | 不输入就没有积累 |
| AI 每次从零开始 | 无限规模（纯 Markdown 只适合几百页量级） |
| 新需求起步慢 | 判断力和品味 |
| 经验无法传承 | 时效性不会自动保鲜（只能靠 lint 提示） |

### 1.2 用户

只有你一个人。设计上不堵死团队共享（脱敏和目录结构都按"可能有第二个读者"来做），但 MVP 不做权限。

## 2. 假设（已确认）

1. 单人使用；规模一年内几百页；MVP 不做检索基础设施。
2. 知识库是独立的 git 仓库，位置固定，由插件配置解析，在任何项目目录里都能用。
3. Claude Code 是主宿主；Codex 共用同一套 skill，hook 不要求两边对等。
4. kb 只写自己的仓库。任何写到 kb 仓库以外的动作都只生成补丁，由你确认后应用。

## 3. 产品形态

两个仓库：**数据**和**产品**分开（Phase 0 调研中，claude-obsidian 也是这么做的，避免插件缓存目录被当成知识库）。

| | 位置 | 可见性 | 内容 |
|---|---|---|---|
| 知识库（vault） | `~/Documents/haigeerlab/kb` → `haigeerlab/kb` | **GitHub 私有** | SCHEMA.md、index、log、inbox、raw、wiki |
| 插件（kb 插件） | 待定，见第 10 节开放问题 1 | 待定 | skills、脚本、hooks、interface.json、测试 |

插件同时作为 Claude Code 插件和 Codex 可读的 Agent Skills 发布。

## 4. 核心概念与知识流

```
采集 ─┬─ 手动 /kb save ──────────────┐（你在场：当场编译，给你看预览）
      ├─ 会话结束：静默记候选指针 ──┐ │
      ├─ delegate 结果：lessons ────┤ │
      └─ /kb learn：外部资料 → raw/ ┤ │
                                   ▼ ▼
                         inbox/（只追加，不删，作为经验类原文）
                                   │ /kb compile（处理积压，逐条确认）
                                   ▼
                         wiki/（编译后的页面：带出处、状态、互链）
                                   │ /kb lint（确定性检查 + 语义检查）
                                   ▼
                         /kb promote → 补丁 → 你确认 → 项目规则 / 全局规则 / skill / eslint
                                   │
                         /kb ask ← 任何项目里的会话、spec-guard（可选探测）
```

**三条铁律**

1. **采集随便，入库严格。** 自动触发只能写 inbox；进 wiki 必须经过编译；升级成规则必须你确认。
2. **出处可核对。** wiki 里的承重事实（数字、日期、版本、引用、命令）必须在 `Raw:` 指向的 inbox 条目或 raw 文件里逐字存在，由脚本校验。
3. **状态机器可读。** 被推翻的结论不删、不静默改写，标 `outdated` 或 `disputed` 并指向取代它的结论；`ask` 默认不把过时结论当作现行答案。

## 5. 使用场景

| # | 场景 | 用户动作 | 期望结果 | 阶段 |
|---|---|---|---|---|
| S1 | 解决完 bug 一句话沉淀 | `/kb save`（可附一句说明） | AI 从当前会话提炼经验，写入 inbox，当场编译成 pitfall 页或更新已有页，给你看改动预览，你点头才写进 wiki | MVP |
| S2 | 在另一个项目里查 | `/kb ask <问题>` | 读 index、全文搜索（含同义词和中英文术语），回答附原文链接；标出已过时的结论 | MVP |
| S3 | 体检 | `/kb lint` | 报告：断链、孤儿页、index 不一致、证据不符、状态块格式错误；语义层面：疑似矛盾、疑似过期、缺页概念、建议升级为规则的条目；附规模指标 | MVP 做确定性部分，语义部分放 Phase 5 |
| S4 | 积压处理 | `/kb compile` | 逐条处理 inbox 积压和候选会话，每条给出处置（新建 / 合并 / 有冲突 / 无新内容），你确认 | Phase 5 |
| S5 | Codex 经验回流 | 无（自动） | kb 读 delegate 的结果文件和答复，抽取 lessons 写入 inbox | Phase 5 |
| S6 | 拆需求前先查 | spec-guard 探测到 kb 时提醒先 `/kb ask` | 能力图里多一节"已知坑与历史决策"，带链接 | Phase 5（改 spec-guard 要走总负责人） |
| S7 | 学新技术 | `/kb learn <技术>` | 调研后原文存进 raw/，生成"原理 / 用法 / 坑 / 搭配 / 最佳实践"主题页，并和项目页互链 | Phase 7 |
| S8 | 升级成规则 | `/kb promote <页面>` | 生成补丁和理由，你确认后应用；原页面记下 `promoted_to` | Phase 6 |
| S9 | 自动采集 | 无（SessionEnd 静默） | 只记 transcript 路径和项目名，不复制内容，不打扰 | Phase 5 |

## 6. 功能需求

### 6.1 命令（用户可见）

| 命令 | 写什么 | MVP |
|---|---|---|
| `/kb save [说明]` | inbox（追加）+ wiki（预览确认后） | ✅ |
| `/kb ask <问题> [--json]` | 不写文件；明确要求归档时，把回答作为新页写入 | ✅（归档在 Phase 5） |
| `/kb lint` | 只输出报告；自动修复仅限"安全修复"（index 一致性、唯一可解析的断链），并写一条 log | ✅（确定性部分） |
| `/kb compile` | inbox → wiki | Phase 5 |
| `/kb promote` | 只生成补丁 | Phase 6 |
| `/kb learn` | raw/ + wiki | Phase 7 |

### 6.2 页面类型（MVP 至少 pitfall、decision 两种）

| 类型 | 必填结构 |
|---|---|
| pitfall | 症状 → 原因 → 解法 → 适用版本/环境 → 如何验证 |
| decision（ADR） | 背景 → 选项 → 决定 → 理由 → 后果 → 状态 |
| tech | 原理 → 用法 → 坑 → 搭配 → 最佳实践 |
| pattern | 问题 → 方案 → 适用条件 → 反例 |
| project | 项目代号 → 技术栈 → 相关坑和决策的链接（枢纽页） |

所有页面都有：frontmatter（type、title、status、created、updated、sources、tags）、`Raw:` 出处、结论段落的状态标记。

### 6.3 确定性部分交给脚本（constraint = quality）

脚本保证、模型不碰的部分：index 和 log 的格式与一致性、断链、frontmatter 必填字段、出处逐字校验（**含状态块**，修掉 karpathy 原脚本跳过状态块的漏洞）、状态字段合法性、脱敏扫描、日期使用本地时区（Asia/Shanghai）。

**写入流程**：模型起草 → 脚本校验 → 不通过就报错并拒绝写入 → 通过后给你看预览 → 写入。不要求事先拼事务 bundle（实跑证明那样摩擦太大）。

### 6.4 脱敏（已确认：抽象化 + 脚本拦截）

- 只记技术本质：症状、原因、解法。不记客户名、品牌、域名、内部 URL、IP、账号、密钥、业务数据、真实用户信息。
- 项目用代号（例如 `proj-starsaas`），代号和真实名称的对照表**不进库**。
- 写入前由脚本扫描：密钥和凭证的正则 + 本地黑名单文件（黑名单本身不进库，放在 `~/.config/kb/` 下）。命中就拒绝写入，并指出位置。
- 自动采集的指针只记路径，不复制会话内容；只有在 compile 时，经过脱敏才进入 inbox。

### 6.5 集成（kb 是可选依赖，不反向耦合）

- kb 发布 `interface.json`，契约包括 `kb ask --json` 的输出结构和版本范围。
- 别的插件按运行时探测的先例（spec-guard → agent-relay）判断 kb 是否可用：只读宿主插件记录和 kb 的 `interface.json`，不起进程、不调 kb 命令。只有探测结果为 `ready`（已安装且版本在支持范围内）时，才注入"先 `/kb ask`"的提醒；`not-installed` 和 `unknown` **完全静默**，流程与没有 kb 时完全一致；`incompatible` 最多提示一句版本不兼容。任何状态都不让对方的命令失败。
- 依赖方向：kb → 任何插件为零依赖；其他插件 → kb 是可选依赖，只认 `interface.json` 里带版本的契约。kb 修改 `ask --json` 的输出结构时必须升契约版本。
- kb 只读别人已公开的产物：delegate 的结果文件和答复。不改 delegate、不用 agent-relay、不读 tier-guard 的日志。
- 任何需要改别的插件的接缝，先登记到 `plugin-ecosystem/SEAMS.md`，由总负责人出方案、你批准。

## 7. 非功能需求

| 项 | 要求 |
|---|---|
| 宿主 | Claude Code 和 Codex 都能用 save / ask / lint；hook 只要求 Claude Code |
| 依赖 | 脚本只依赖 Python 3 标准库或 Node 内置模块，不引入运行时依赖 |
| 可读性 | Obsidian 直接打开就能用；链接在 Obsidian 和 GitHub 上都能解析；raw 不放隐藏目录 |
| 语言 | 正文用中文，术语、API、命令、报错原文保留英文；文件名用英文 kebab-case；标题用中文 |
| 摩擦 | 一次 `/kb save` 从输入命令到写入 wiki，你需要做的只有一次确认 |
| 规模 | 以下任一条件出现时评估引入 qmd：wiki 超过 300 页、index 超过 40KB、ask 平均读文件超过 15 个。lint 每次输出这三个数 |
| 可恢复 | 所有写入都在 git 里；kb 不自动 commit 或 push，提交由你决定（或由 `/kb save` 在确认后做一次本地 commit，见开放问题 2） |

## 8. 边界

- **始终**：写入前跑校验脚本；保留出处；被推翻的结论标状态、不删除；日期用本地时区。
- **先问**：写 wiki 以外的任何位置；合并或删除已有页面；联网抓取（learn）；push 到远端。
- **绝不**：未经编译直接改 wiki；自动修改别的仓库；把会话全文存进库；写入没通过脱敏扫描的内容；把知识库内容同步到公开仓库（包括 frontend-knowledge-tree）。

## 9. MVP 验收标准（修订版）

1. 在一个真实项目里解决一个问题后，`/kb save` 一条命令就把经验写进 inbox，并编译成 wiki 页；你只做一次确认。
2. 编译后，wiki 页带 `Raw:` 出处并通过出处校验；与已有页面互相链接；index.md 和 log.md 同步更新。
3. 在**另一个**项目的会话里 `/kb ask`，能检索到这条知识并附上来源；被标为过时的结论不会被当作现行答案。
4. Claude Code 和 Codex 都能跑通 save 和 ask（Codex 需要实测，派 Codex 前先征得你同意）。
5. `/kb lint` 至少能发现断链、孤儿页、index 不一致、出处不符四类问题，并输出报告。
6. 包含密钥或黑名单词的内容会被拒绝写入（有测试）。
7. 所有自动行为只写 inbox；没有任何代码路径能绕过编译直接改 wiki，也没有任何代码路径会改 kb 仓库以外的文件（有测试）。
